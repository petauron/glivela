# Vastora 应用入口直达 Glivela（MVP）

## 访问链路

Vastora 已登录用户打开应用，签名 UI 直接挂载 Glivela 面板。浏览器通过同源的 `/api/v1/applications/{id}/panel/v1/admin/{operation}` POST JSON 请求；Center 每次检查会话和 CSRF，再转发到数据库中该应用的私网 controller 服务。账号、线路、订阅、流量和网络优化仍由独立 Glivela 后端处理。

不增加说明页、浏览器证书安装或客户端私网接入步骤。安装未完成、服务不可达、登录过期分别显示实际错误，不能将端口可达视为业务验收完成。

## 服务端身份

安装或更新时，Center 自动生成并保留每节点 Glivela 专属的管理身份，使用现有加密 secrets 存储。系统管理字段 `panel_access_json` 不接受用户输入。配方仅给控制端提供服务器证书、服务器私钥、CA 和公开的客户端证书；客户端私钥只保存在 Center，不发给浏览器或 Glivela。

原私网监听地址和节点 CA 保持不变。固定 SNI `panel.glivela.internal` 选择独立的 TLS 1.3 双向认证身份，只有登记的准确客户端证书指纹能管理应用。节点证书不能获得管理权限。Center 不转发浏览器 cookie、认证头或上游跳转，不接受用户指定目标地址。

证书有效期十年，过期失败关闭，不跳过证书校验。备份恢复必须保留 Center 数据库及其加密密钥，并保留应用持久数据与凭据。当前没有自动轮换功能；到期前需显式协调轮换双方身份，不能单边删除 secret 或重置业务数据。

## 交付顺序与边界

1. 先发布包含面板访问能力的 Glivela 程序及 UI，通过既有 Release Please 和 CI。
2. 更新 Center，提供同源传输和自动凭据供应。
3. 将签名目录固定到该 Glivela 不可变发布资产及镜像，纳入新的受管凭据配方，再升级控制端；网络优化还需升级对应节点程序。
4. 使用已有 Vastora 登录态打开应用，确认真实面板读取、操作权限和错误状态，再按授权范围验证业务。

源码、CI、签名目录发布、运行时升级和实际验收分别记录到对应主 issue。
